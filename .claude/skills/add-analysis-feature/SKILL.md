# 分析機能をルールとして追加する

finplan では「このカテゴリーはこう扱う」をコードに書かない。分析に必要な**機能**を作り、それを**どの期間・どのカテゴリー・どのメモ**に当てはめるかを設定（ルール）で決める。

## 1. まず既存の機能で足りるか確かめる

今あるルールの部品:

| 種類 | 項目 | 意味 |
|---|---|---|
| 条件 `RuleMatch` | `category` | CSVに書かれていた元のカテゴリー |
| | `memo` / `memoIsRegex` | メモに含む文字（正規表現も可） |
| | `from` / `to` | 日付の範囲（YYYY-MM-DD、両端を含む） |
| 効果 `RuleEffect` | `category` | カテゴリーを付け替える（新しい名前でもよい） |
| | `groupId` | グループを変える（役割 `ignore` のグループに入れれば除外） |
| | `amortizeMonths` | 取引月から N か月に均等に割って計上する |

足りるなら、コードは変えずに `src/config/local/default-config.json`（個人の設定、Gitの管理対象外）にルールを足す（または画面で足すよう利用者に提案する）。
`src/config/default-config.json` はコミットされるので、利用者のカテゴリー名やメモに基づくルールは書かない。
対象の取引は `npm run inspect -- csv/<file>.csv --category <名前>` などで先に確認する（`inspect-data` スキル）。

## 2. 足りない場合は汎用的な部品として足す

依頼を「何をしたいか」に言い換え、どのカテゴリーにも使える形にする。
例: 「家賃は前払いなので1か月後ろにずらしたい」→ 効果 `shiftMonths: number`。「家賃カテゴリー専用の処理」にはしない。

手順:

1. **型**: `src/domain/types.ts` の `RuleMatch` か `RuleEffect` に、省略できる項目として足す。JSDoc で意味を書く。
2. **判定・適用**: `src/domain/classify.ts`
   - 条件なら `matchesRule` に足す。`isActive` が「条件が1つ以上ある」と判定できるようにする。
   - 効果なら `classify` の中で適用する。`effectFor` は後のルールで上書きする仕組みなので、新しい項目もそれに従う。
   - 取引を増やす・動かす効果（按分など）は、`classify` の戻り値を展開する形にする。集計側（`aggregate.ts`）は変えずに済むようにする。
3. **画面**: `src/components/RuleEditor.tsx` の「条件」または「効果」の行に入力欄を足す。
4. **テスト**: `src/domain/classify.test.ts` に、架空のカテゴリー名のデータ（共通のものは `testData.ts`）でテストを足す。期間の境界、無効なルール、他の効果との重なりも確かめる。
5. **設定の互換性**: 今はまだ後方互換を考えない段階なので、移行処理は書かない。形を変えたら `src/config/default-*.json` と `src/config/local/default-*.json` を新しい形に直す。
6. **ドキュメント**: `CLAUDE.md` の「ルールの意味」と、このスキルの表を更新する。
7. 確認: `npx tsc -b`、`npm test`、`npm run lint`。実データで効果を見るなら `npm run inspect`。

## してはいけないこと

- カテゴリー名やグループIDで分岐するコードを書く（`if (category === '家賃')` など）。
- 集計（`aggregate.ts` / `stats.ts`）の中で特定の取引を特別扱いする。扱いの違いはすべて `classify` までで決める。
- 実データのメモの中身（人名・取引先など）をテストやコードに書き写す。
