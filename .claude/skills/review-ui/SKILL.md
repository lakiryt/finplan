# UIの見直し

説明文を足して解決しない。操作した結果と、保存される内容が見えれば、説明は要らない。

## 完了前に確かめること

1. **保存される内容が、保存する前に見えるか。** 何を選んでいて、保存すると何が起きるかを、結果の形で見せる（例: 3. に並ぶのと同じバッジ、件数と金額）。「何も選んでいないように見える」状態を作らない。
2. **同じ入力欄が2つの意味を持っていないか。** 検索なのか条件なのかが状況で変わるなら、モードを分けて、今どちらかを見せる。暗黙の切り替え（1件選ぶと保存内容が変わる、など）をしない。
3. **画面の主役は目的と合っているか。** 条件の画面なら条件が主役で、例外的な操作（1件ずつ選ぶ）はあえて選んだときだけ出す。
4. **説明文を消しても使えるか。** 書いた説明を1つずつ消してみて、困るなら文言ではなく形（ボタンの名前、状態の表示、薄く出す、選べなくする）で伝える。残すのは、見ただけでは分からない制度上の事実や、取り返しのつかない操作の確認だけ。詳しい説明は `docs/` に置く。
5. **押せない・変わらない理由が、状態で分かるか。** 灰色にするなら、近くに理由が見える（例: 「今の加工」の列に「除外」）。
6. **操作で見ている物が動かないか。** 押す場所が動くと続けて押せない。選んだ結果は別の場所に出す。
7. **主な操作が画面の中に見えているか。** 一覧が長くなっても保存ボタンが隠れない。見本のデータは実データより少ないので、項目を増やした状態でも見る。数の上限（表示は200件まで、など）が操作の結果を黙って変えない。
8. **ラベルが要るのは、置き場所が悪いからではないか。** ラベルや説明を書く前に、入力欄や情報ごとに「この画面での役割は何か」を考え、役割に合う場所と見た目に置く。名前ならタイトルの位置に見出しの大きさで、合計なら表の下に、主な操作なら最後に。置き場所で伝われば、ラベルは要らないか小さくて済む。新しい欄は、既存の欄の並びの端に足さず、画面全体を見て置き場所を決める。
9. **実際に見る。** 型やテストが通っても画面は確かめられていない。ブラウザか Edge の headless のスクリーンショットで見る。モーダルなど操作が要る画面は、一時的なプレビューを作って見て、消す。押せるかどうかは、Edge を `--remote-debugging-port` で起動して実際にクリックして確かめる。見ていないなら、そう報告する。

小さく直せるものはそのまま直す。作り直しになるものは、案を添えて利用者に確かめる。
